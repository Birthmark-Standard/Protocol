# Birthmark Protocol — Per-Leg Message Specification

**Notation.** `||` = concatenation. `ECIES(pk; m)` = randomized IND-CCA2 public-key encryption. `AEAD(k; m)` = AES-256-GCM. `Sign(sk; m)` = Ed25519. `RSign(R; m)` = unlinkable 1-of-n ring signature over ring R.

## Parties and keys

Every key has one purpose. No key is used both to decrypt and to sign, and no node uses one key for two roles.

| Party | Key | Type | Purpose | Public part known to |
| --- | --- | --- | --- | --- |
| Device | cred\_D | secret credential | Proves membership to its validator | Validator (key table), no one else |
| Device | key\_ref | identifier | Tells the validator which key-table entry to use | Validator |
| Validator V | V-token\_sk / pk | ECIES | Decrypts the device token | Devices (provisioned) |
| Validator V | V-sign\_sk / pk | ring member key | Member key in Ring V, for signing a verdict | C, gatekeepers |
| Validator V | V-transit\_sk / pk | ECIES | Terminates the C→V leg | C |
| Credential processor C | C-device\_sk / pk | ECIES | Relay terminus for the credential packet | Devices (device table) |
| Credential processor C | C-ring\_sk / pk | ring member key | Member key in ring R for signing PacketHash and the verdict | Gatekeepers, F, I (as part of R) |
| Gatekeeper G\_k (k = 1..3) | Gk-term\_sk / pk | ECIES | Terminates the C→G\_k leg | C |
| Gatekeeper G\_k | Gk-sign\_sk / pk | Ed25519 | Countersigns board postings | F, I |
| Content server F and I | F-device\_sk / pk | ECIES | Relay terminus for the content packet | Devices (device table) |
| Content server F and I | F-id\_sk / pk | Ed25519 | Signs registry submissions | Registry |
| Every submission server S | S-transit\_sk / pk | ECIES | Terminates every transit leg addressed to S, whatever role S holds in that transaction (Addressed hop, Random hop, C, F or I) | Every other submission server (full transit-key table) and every device (device table) |

**Transit keys belong to servers, not roles.** A, B, C, D, E, F, G, H and I are per-transaction roles, and any submission server can hold any of them, subject to the role rules below. Each server therefore holds one transit key pair and a full table of every other server's transit public key. "A-transit", "C-transit" and so on in the leg table mean the S-transit key of whichever server holds that role for a given transaction. The V→C leg also uses C's S-transit key, so validators hold the transit-key table too — this follows from position labels naming roles rather than server identities: a role-specific keypair for every role a server might ever be assigned would work against that principle, not with it.

**Per-transaction values** (fresh each transaction, never reused):

- `n`: 128-bit content nonce. Goes only to F and I.
- `tx_nonce`: 128-bit replay nonce. Goes only to V, inside the token.
- `claim`: the device's statement about post-capture processing. Zero for a hardware capture. For an edit, the editing application's measured deviation from the parent record. Goes only to V, inside the token. Sizes below assume a one-byte claim; the encoding of an edit's deviation is not fixed here.
- `verdict`: one byte, derived by V as `judge(claim)`: a modified bit and a two-bit deviation bucket (four classes), reserved bits zero. Zero for an unedited capture. A modified verdict is a flagged record, not a rejection. The device never sends a verdict or a modification level. The bucket boundaries are a deployment parameter set by the editing application and its developer; the protocol treats the bucket as an opaque value. Bit positions are not fixed here.
- `BK` (BlindShare\_key): 256-bit AEAD key. Generated by C, fresh per transaction. Never sent by the device; goes from C to the gatekeepers.

**Ring R:** the ring public keys of the C-candidate pool minus the three currently active gatekeepers. Verifiers check against the ring that is current at verification time. Ring keys are separate from every other node key. Over a 17-node pool, σ\_C is 576 bytes.

**Ring V:** the ring public keys of every registered validator. Unlike Ring R, whose size is fixed by the submission-server pool, its size is the number of registered validators, which starts at one and grows only as more validators register; an unlinkable ring signature over a one-member ring carries no anonymity benefit across validators (there is only one to hide among) and is close to the cost of a plain signature, well under σ\_C's 576 bytes. Hiding which validator signed is a benefit that strengthens only as more validators join.

## Device-side construction

The device builds one credential packet and two content packets per transaction, then wraps each for its first relay hop. C, not the device, generates the blinding key and the blinded commitment, once it receives PacketHash from the device; the device never computes or holds either.

1. `ContentHash = SHA-256(candidate image)`. A candidate image is the RAW file, the ISP-processed image, or an adjusted version that clears the deviation threshold.
2. `n` ← 128-bit random.
3. `PacketHash = SHA-256(ContentHash || n || flags || [h(metadata)] || [parent ContentHash])`. `flags` is one byte: bit 0 set if h(metadata) is present, bit 1 set if the parent ContentHash is present, other bits zero. The flags byte and the fixed 32-byte field length make the encoding unambiguous. PacketHash therefore covers every field the content packet carries, so F and I cannot alter an optional field without changing PacketHash.
4. `tx_nonce` ← 128-bit random.
5. `Token = ECIES(V-token_pk; cred_D || tx_nonce || claim)`. With a 32-byte cred\_D and a one-byte claim this is 98 bytes.
6. `P_C = ECIES(C-device_pk; Token || key_ref || PacketHash)`.
7. `P_F = ECIES(F-device_pk; ContentHash || n || [h(metadata)] || [parent ContentHash])`, and `P_I` the same under I-device\_pk. The bracketed fields are optional; the parent ContentHash is present only for an edit. Each optional field adds 32 bytes, which the leg padding absorbs. The content packet carries no modification level: F and I take the verdict from the gatekeeper quorum.
8. First-hop wraps: `Cred-1 = ECIES(A-transit_pk; rc_C || P_C)`, `ContA-1 = ECIES(D-transit_pk; rc_F || P_F)`, `ContB-1 = ECIES(G-transit_pk; rc_I || P_I)`. `rc_X` is the 16-byte routing code for destination X, resolved via the table-stack mechanism described under Routing code resolution.

### Operation count per transaction

| Operation | Count | Notes |
| --- | --- | --- |
| ECIES encryptions | 7 | Token, P\_C, P\_F, P\_I, and three first-hop wraps |
| Scalar multiplications | 14 | Each ECIES encryption = one fixed-base (ephemeral key) + one variable-base (shared secret) |
| AEAD over small inputs | 7 | The symmetric part of each ECIES encryption. Under 1,000 bytes total. |
| SHA-256 over the candidate image | 1 per image | Dominant cost: roughly 430–600 ms per 25–35 MB image at 13.7 cycles/byte, 800 MHz |
| SHA-256 over small inputs | 1 | PacketHash |

**Estimated elliptic-curve cost**, at 527,102 cycles per variable-base multiplication (Cortex-A8 at 800 MHz): 3.7M cycles (4.6 ms) if fixed-base cost is ignored, up to 7.4M cycles (9.2 ms) if fixed-base costs the same as variable-base. Precomputed fixed-base multiplication is usually cheaper, so the real figure falls in between.

## Role selection and path disjointness

Each transaction uses nine distinct nodes across its three paths, plus the three active gatekeepers.

1. **Gatekeepers:** the three currently active gatekeepers, a known rotating set, serve every transaction. They never serve as C, F or I for that transaction.
2. **C:** the device picks C at random from the device table, after excluding entries in its own validator's jurisdiction. The routing code rc\_C is the per-transaction identifier for this destination.
3. **F and I:** picked at random from the pool minus the gatekeepers, with F ≠ I. The choice must not depend on the device, manufacturer or jurisdiction, because F and I are named on the public registry record.
4. **Path disjointness:** the sets {A, B, C}, {D, E, F} and {G, H, I} share no node. No node on the credential path appears on either content path, for that transaction.
5. **First hops:** A, D and G are distinct and are never C, F or I, for that transaction.

**A Random hop (B, E, H) may coincide with C, F or I for a different transaction.** This is safe: a Random hop decrypts only its own transit wrapper, revealing the routing code and destination but never the payload itself, which stays encrypted under the destination's own key. Its own observations therefore reveal nothing about device identity or content for that transaction, so there is nothing to link to a later, unrelated transaction where the same server plays C, F or I.

**An active gatekeeper may also serve as a first hop (A, D or G) for a different transaction.** This carries no correlation risk: the Addressed hop never resolves the routing code it carries, so it never learns a packet is even destined for C, let alone which C; the payload is encrypted under C's own key, which a first hop structurally never holds. No shared value or resolved destination links the two roles.

### Routing code resolution

Resolution has to give every possible Random hop the ability to resolve a code locally and offline, while denying that same ability to whichever specific server the device happened to pick as the Addressed hop for that transaction — without a live query to any third party, since a party consulted on every transaction would itself become a new, system-wide observation point.

Each server in the pool holds a **stack of tables**, one per server in the pool. The table labeled for server X contains exactly the routing lines where X is the Addressed hop, and is distributed to every server *except* X. A server's own stack is therefore the union of every other server's labeled table — every routing line in the current device table, except the lines belonging to routes where that server itself is the Addressed hop.

Resolving `rc_C` (or `rc_F`, `rc_I`) is a local, offline lookup against this stack. Whoever the device picked as the Random hop for a given path holds the table containing that path's routing line, since it is essentially never the same server as that path's Addressed hop, and resolves normally. The Addressed hop itself is the one server in the entire pool whose stack is missing precisely the table containing its own transaction's line, so it cannot resolve the code even given full access to everything it holds. This gives a cryptographic-strength guarantee from a routing property, not a policy one: there is no check to bypass, because the information simply is not present.

The cost is a stack roughly twenty times the size of a single routing table, and a rebuild of the whole stack whenever the device table or the pool composition changes. How often this happens is not yet fixed; the natural triggers are gatekeeper rotation, device-table updates, or both. When gatekeeper rotation triggers a rebuild, the new stack uses a fresh set of routing codes that does not overlap any code from the previous set, rather than reassigning the same codes to a new gatekeeper set: a packet carrying an old-generation code continues to resolve to the old gatekeeper set until it drains from the system, while a packet carrying a new-generation code resolves to the new set, so the handover is gradual rather than a synchronized cutover. How long an old-generation code remains routable, bounding how long the old set stays live, is not yet decided.

## Per-leg message table

There are 19 legs per transaction on the wire, plus board reads by F and I. Every leg except the registry submissions is padded inside its transit encryption to a size drawn uniformly from its class: **420–460 B** for all legs except the gatekeeper fan-out, which uses **820–860 B**. Raw sizes marked \* are estimates (32-byte cred\_D, one-byte claim, 16-byte tx\_id, 8-byte key\_ref); unmarked sizes are measured directly.

| Leg | From → To | Contents | Encrypted under | Receiver learns | Raw size |
| --- | --- | --- | --- | --- | --- |
| Cred-1 | Device → A | rc\_C, P\_C | A-transit | Device IP; nothing else readable | 252 B\* |
| Cred-2 | A → B (random) | rc\_C, P\_C | B-transit | A's address; rc\_C | 252 B\* |
| Cred-3 | B → C | P\_C | C-transit | B's address; P\_C contents: Token (opaque), key\_ref, PacketHash | 236 B\* |
| ContA-1 | Device → D | rc\_F, P\_F | D-transit | Device IP | 162 B |
| ContA-2 | D → E (random) | rc\_F, P\_F | E-transit | D's address; rc\_F | 162 B |
| ContA-3 | E → F | P\_F | F-transit | E's address; ContentHash, n, and any optional fields | 146 B |
| ContB-1–3 | Device → G → H → I | as ContA, with rc\_I and P\_I | G-, H-, I-transit | as ContA, for I | 162 / 162 / 146 B |
| CV-1 | C → V | tx\_id, Token, key\_ref, EncPH | V-transit | cred\_D, tx\_nonce, claim, EncPH (opaque without BK) | 219 B\* |
| CV-2 (verdict) | V → C | tx\_id, verdict, σ\_V | C-transit | The verdict and σ\_V; EncPH is not sent again, since C already holds it from step 2. The verdict byte takes the place of the former approval flag. | 133 B\* |
| CV-2 (reject) | V → C | tx\_id, REJECTED | C-transit | Rejection (unregistered credential). **No signature.** Padded to the same class as a verdict. | 69 B\* |
| GK-k (k = 1..3) | C → G\_k | PacketHash, verdict, σ\_V, BK, σ\_C | Gk-term | PacketHash; the verdict; that some ring member of Ring V signed (not which one); that some ring member signed C's ring too; EncPH is not sent, since the gatekeeper recomputes it from BK and PacketHash | 690 B\* + Ring V's own size |
| Post-k | G\_k → Board\_k | PacketHash, verdict, σ\_C, σ\_Gk | Registry-node access only | — | 32 + 1 + 576 + 64 B |
| Reg-F | F → Registry | ContentHash, verdict, [h(metadata)], [parent ContentHash], σ\_F | Registry transport | ContentHash and the other submitted fields; F's identity | 98 B, plus 32 B per optional field |
| Reg-I | I → Registry | ContentHash, verdict, [h(metadata)], [parent ContentHash], σ\_I | Registry transport | ContentHash and the other submitted fields; I's identity | 98 B, plus 32 B per optional field |

**Signatures:**

- `σ_V = Sign(V-sign_sk; verdict || EncPH)` — produced for every verdict, including a modified one; **not** produced on rejection.
- `σ_C = RSign(R; PacketHash || verdict)` — 576 B for a 17-member ring.
- `σ_Gk = Sign(Gk-sign_sk; PacketHash || σ_C)`.
- `σ_F = Sign(F-id_sk; ContentHash || verdict || [h(metadata)] || [parent ContentHash])`, and σ\_I the same under I-id\_sk. Signing every field the record carries, and computing PacketHash over the optional fields, means neither content server can be made to vouch for a record whose verdict or optional fields differ from what the quorum and the device supplied: a server that alters an optional field computes a PacketHash' that no quorum covers. Both σ\_V and σ\_C cover the verdict, so no party after V can change it. σ\_V, σ\_C and σ\_Gk are never posted to the registry; the only signatures a registry record holds are σ\_F and σ\_I.

`tx_id` is 16 random bytes generated by C per transaction.

**Public verification** is not part of a transaction: a verifier sends a locally computed ContentHash to the registry and receives the record, if one exists.

## Decoy traffic

The system injects decoy transactions to enlarge the candidate pool available to a single compromised component beyond whatever real traffic volume happens to be, and to prevent an observer from estimating real traffic volume from total traffic volume.

A decoy transaction is a genuine transaction from a genuinely registered device credential, not a distinguishable, invalid, or specially marked one. The credentials belong to a pool of identities operated by the same infrastructure that generates decoy traffic and distributes the routing-code table, registered with a validator the same way any other device is. Nothing about a decoy transaction differs structurally from a real one at any stage: V approves it normally, C fans it out normally, every signature is genuinely valid, gatekeeper verification and board quorum proceed normally, and F and I finalize a registry record for it exactly as they would for real content. No party, including V, C, and the gatekeepers, has any way to distinguish a decoy transaction from a real one, because there is nothing structurally different to distinguish. A decoy is an ordinary submission with arbitrary content. Its claim, and therefore its verdict, follows the mix of claims in real traffic, so a decoy record carries a verdict as a real one does and no verdict marks a record as real. The decoy-identity pool must be large enough that no single identity's submission rate looks statistically different from a plausible device's. The pool size is expected to vary with the deployment's own phase and scale, and is not meant to be fixed to a single documented number; it is an operating parameter the deploying infrastructure adjusts as needed, using as many rotating identities as the deployment's own scale calls for.

Decoy traffic follows the same per-transaction construction as real traffic in every respect, including the 2:1 content-to-credential ratio real traffic already produces on its own, so the aggregate ratio stays uninformative about what fraction of traffic is decoy. The injection target is fixed, not scaled to real traffic volume: 60 ± 10 transactions in flight at any given time, regardless of how much real traffic exists. Decoy volume tops up whatever real traffic falls short of this target. The randomized range, rather than a single exact constant, keeps the target from being a precisely known value an observer could characterize and subtract out exactly; it does not eliminate the risk that enough observed windows could statistically narrow the underlying distribution.

Every decoy-produced registry record is permanent, exactly like a real one; none are ever removed. Whether and how to prune decoy records to manage hot-storage growth is an open implementation question, deferred rather than specified here.

The Random relay hops (B, E, H) see no difference between decoy and real traffic at any injection rate, since they only ever observe opaque ciphertext.

## Hold timing

Every hold in this spec draws from the same lottery shape — a 10-second tick, geometric release, capped at 3× the hold's own mean — but no longer shares one baseline mean. Each stage's per-tick release probability and cap are set independently to hit that stage's own target mean. The departure bundle inclusion lottery uses a 30-second tick (one per bundle boundary) with a cap at 12 boundaries (3× its 120-second target mean). Settled means:

| Stage | Mean | Std dev | CoV |
| --- | --- | --- | --- |
| Relay hops (A, B, D, E, G, H), every path | 120 s | 100.7 s | 0.84 |
| Device's credential-channel hold | 120 s | 100.7 s | 0.84 |
| Device's content-channel holds (both) | 240 s | 201.4 s | 0.84 |
| C's hold before sending CV-1 | 30 s | 25.2 s | 0.84 |
| V's hold before sending CV-2 | 30 s | 25.2 s | 0.84 |
| C's fan-out to each gatekeeper (independent per leg) | 60 s | 50.3 s | 0.84 |
| Gatekeeper's own hold | 30 s | 25.2 s | 0.84 |
| Departure bundle inclusion lottery | 101 s | 90.9 s | 0.90 |
| F/I's pre-match hold | 240 s | 201.4 s | 0.84 |
| Post-match lottery | 30 s | 25.2 s | 0.84 |
| Registry bundle wait | 60 s | 50.3 s | 0.84 |

Only stages with a legitimate basis for knowing their own role carry a value different from the shared 120 s figure: the device knows which channel it is constructing a packet for, and F/I know they are F or I. Relay hops cannot carry a role-specific parameter at all, per the Addressed hop's path-blindness constraint below, so every relay hop and the device's own credential channel share the same, unelevated 120 s mean. The device's content channels and F/I's pre-match hold share the elevated 240 s mean — exactly double the shared baseline, settling the earlier open choice between that figure and a higher one.

## Departure bundling

The gatekeeper's own hold (see Hold timing) already randomizes when a given packet is selected for release. Departure bundling changes what happens after selection, not the selection itself.

Once a packet's own hold has expired, it does not depart in the next bundle automatically. Instead, at each successive 30-second boundary it draws independently for inclusion in that boundary's bundle: 25% chance of boarding, 75% chance of carrying over to the next boundary. The cap is 12 boundaries (360 seconds, exactly 3× the 120-second mean), after which the packet is included unconditionally. This gives a measured mean inclusion-lottery wait of 101 seconds (see Hold timing); the cap's truncation of the geometric tail brings the realized mean below the 120-second value the uncapped geometric would predict. Bundles therefore contain a mix of packets from a range of arrival times — packets that became ready moments apart can land in different bundles, and packets that became ready up to 360 seconds apart can land in the same one. The earlier, simpler version (every ready packet joined the very next boundary) narrowed this mixing window to near zero, handing a patient observer direct correspondence between "ready time" and "departure bundle."

Packets within the same bundle have no observable order relative to each other, since they depart at the same moment. Measured at the settled operating point (60 decoys in flight): mean 2.33 postings per bundle at one gatekeeper, 32.4% of bundles hold fewer than two postings, and 10.0% are empty.

Whether the first-hop relay lottery should receive the same bundling treatment is open.

## Registry-level bundling

A content server's own confirmed submission, once quorum forms, does not submit to the registry immediately. Instead, it waits for the next registry-level departure bundle, which pools confirmed submissions from every F/I server in the pool, not just the submitting server's own, and commits them together on a shared schedule.

Pooling across the whole F/I population rather than bundling each server's own submissions separately gives a materially larger, more reliable bundle size, for the same reason the decoy target's volume is what makes gatekeeper-level bundling work at all: a bundle drawn from one server's own share of traffic is far smaller than one drawn from the whole pool's aggregate rate.

This does not conflict with the registry's own finalization rule. Two distinct identities agreeing on a record is a property of who submitted it; a shared commit schedule governs only when the registry acts on submissions that already satisfy that rule, not whether they satisfy it.

Decoy transactions, which now complete the full pipeline through to a genuine registry record (see Decoy traffic), participate in registry-level bundling the same way they participate in gatekeeper bundling, and for the same reason: they are what gives any given window enough volume to bundle meaningfully.

The wait for this bundle has a mean of 60 seconds (see Hold timing), settling the window size against the measured rate of confirmed submissions arriving at the registry.

This is an additional hold on top of every other hold already in the pipeline; a real submission does not finalize until the gatekeeper's own hold and bundle, the content server's own node-clock hold, and this registry-level bundle have each had their turn. The added latency is real and has not been bounded here.

## Post-match lottery

F and I each independently watch the same boards for the same quorum condition. If quorum takes
longer to form than either server's own pre-match hold (see the content servers' own steps), both
servers spend that time simply waiting on the same external event, and the instant it resolves,
both detect it and both submit at essentially the same moment. Two registry submissions arriving
together is itself a precise, directly observable marker of when quorum completed, and this
marker's quality gets worse as credential-side processing gets slower: at a quorum-formation time
of several minutes, the two submissions land within 5 seconds of each other more than three
quarters of the time.

Each server draws its own, independent delay after quorum is confirmed — mean 30 seconds (see Hold timing) — timed from the moment quorum is actually confirmed rather than from its own, earlier pre-match hold. This keeps F's and I's relative submission timing independent of quorum-formation speed even in the worst case (slow credential-side processing, where both pre-match holds get overtaken by the wait for quorum), and adds further separation on top of the pre-match hold's own randomness in the common, faster case. Keeping the pre-match hold and adding this lottery therefore performs at least as well as the lottery alone everywhere, and strictly better wherever the pre-match hold still matters.

## Checks and actions at each party

Any failed check drops the transaction and triggers that party's discard obligations. No party signs, posts or forwards after a failed check.

### Relay hops

- **Addressed hop (A, D, G):** decrypts its transit layer, reads the routing code but cannot resolve it (its own stack is missing exactly this line), picks a random next hop (never itself), re-encrypts `rc || payload` for it, holds per the relay timing lottery, then forwards. An Addressed hop cannot tell which of A, D, or G it is playing for a given transaction: its payload is opaque ciphertext regardless of path, and its routing code is deliberately unresolvable and carries no visible tag distinguishing credential-path from content-path codes, since such a tag would itself be observable. Path-specific timing therefore lives elsewhere — see Hold timing.
- **Random hop (B, E, H):** decrypts, resolves the routing code to the destination using its own table stack, holds, then forwards the payload alone under the destination's transit key.

### Credential processor C

1. Decrypts Cred-3, then P\_C. Obtains Token, key\_ref, PacketHash.
2. Generates BK, computes `EncPH = AEAD(BK; PacketHash)`. A fixed AEAD nonce is safe because BK is single-use.
3. Generates tx\_id. Holds (see Hold timing), then sends CV-1 (tx\_id, Token, key\_ref, EncPH) to the validator that key\_ref designates.
4. On **REJECTED**: drops the transaction.
5. On a **verdict**: verifies σ\_V over `verdict || EncPH` with the EncPH it holds; a failed verification drops the transaction. Computes `σ_C = RSign(R; PacketHash || verdict)`. C signs only a verdict that V issued for this transaction.
6. Sends GK-1, GK-2 and GK-3, each carrying PacketHash, verdict, σ\_V, BK and σ\_C, encrypted separately. Each of the three legs draws its own, independent delay (see Hold timing) starting from when C received CV-2 in step 3; this is what "staggered" means here, not spacing the three legs relative to each other after an unheld first send.

### Validator V

1. Decrypts CV-1's transit layer, obtaining tx\_id, Token (still opaque), key\_ref, EncPH. Decrypts Token to obtain cred\_D, tx\_nonce, claim.
2. Checks membership of cred\_D in the key-table entry that key\_ref names.
3. Checks that tx\_nonce is not in its transaction log, then logs `(tx_id, tx_nonce)` for up to 3 years.
4. Holds (see Hold timing), then: both pass, computes `verdict = judge(claim)`, signs `verdict || EncPH` and replies with the verdict and σ\_V; either fails, replies REJECTED with no signature. A modified verdict is a flagged record, not a rejection.

### Gatekeeper G\_k

1. Decrypts GK-k. Obtains PacketHash, verdict, σ\_V, BK, σ\_C.
2. Recomputes `EncPH = AEAD(BK; PacketHash)` from the BK and PacketHash it just received, then verifies σ\_V, over `verdict || EncPH`, against Ring V. A mismatched BK or PacketHash would produce a different EncPH than the one V actually signed, and a different verdict would not verify, so this single check does the work a separate decrypt-and-compare step would otherwise duplicate.
3. Verifies σ\_C, over `PacketHash || verdict`, against the current ring R.
4. Holds on its own hold clock (see Hold timing), then waits for the next departure bundle per Departure bundling.
5. Posts `(PacketHash, verdict, σ_C, σ_Gk)` to Board\_k, together with every other packet in the same departure bundle.

### Content servers F and I

1. Decrypt the last content leg, then P\_F. Obtain ContentHash, n and any optional fields.
2. Compute `PH' = SHA-256(ContentHash || n || flags || [h(metadata)] || [parent ContentHash])` from the fields in the packet, with `flags` set from which optional fields are present.
3. Holds on its own node clock before checking the boards (see Hold timing).
4. Proceed once PH' appears with the same verdict on at least two distinct boards, each posting with a valid σ\_Gk and a valid σ\_C against the current ring. The verdict F and I record is the one the quorum agrees on. Boards that disagree on the verdict do not form a quorum for either pair. If quorum does not form within 30 minutes, drop.
5. Holds again, per Post-match lottery.
6. Waits for the next registry-level departure bundle per Registry-level bundling.
7. Submit Reg-F (or Reg-I), carrying the quorum's verdict, together with every other submission in the same registry-level bundle.

### Registry

1. Verifies each submission's signature against the known server identity keys.
2. Finalizes a record once two submissions from two **distinct** identities agree on every field: ContentHash, verdict, and any optional fields.
3. Duplicate collapse: a ContentHash already on the registry is matched to the existing record, not re-posted.
4. Stamps the record with a coarsened timestamp.

## Discard and retention obligations

No party keeps any value that would let it, or a later inspector, pair one leg of a transaction with another. The only per-transaction records that survive are the validator's nonce log (with a shelf life), the board postings, and the finalized registry record.

| Party | Must discard | When | May retain | Audit |
| --- | --- | --- | --- | --- |
| Addressed hop (A, D, G) | Routing code, and any record of which code went with which packet | On forwarding | Operational logs with coarse timestamps only | Submitter-initiated routing-code sweep |
| Random hop (B, E, H) | Routing code and resolved destination for the packet | On forwarding | Same | Submitter-initiated routing-code sweep |
| C | Token, key\_ref, PacketHash, BK, tx\_id, EncPH, verdict, σ\_V | After the last GK leg is sent, or at once on rejection or failure | Nothing per transaction | PacketHash / BK / EncPH sweep |
| V | claim, verdict, EncPH, σ\_V | After sending CV-2 | Log entry `(tx_id, tx_nonce)` for up to 3 years. **Never** stored with cred\_D, key\_ref or EncPH. | Schema attestation |
| G\_k | BK, EncPH, σ\_V | After posting, or at once on failure | Its own posting on Board\_k | PacketHash / BK / EncPH sweep |
| Board\_k | — | — | Postings, for 30 minutes | — |
| F, I | n, PH', and ContentHash if not submitted | After submitting, or on quorum timeout | Nothing per transaction | Submitter-initiated n sweep |
| Registry | — | — | Finalized record, permanently | Public |

**Audit method:** a submitter supplies ContentHash, n and any optional fields from their own past transaction. The governance body recomputes PacketHash and searches the named parties' logs for any residual copy. The sweep covers gatekeepers and content servers as well as C and the boards, since all four hold values it can recognize.

## Observables per party

No single party holds both a device identity (cred\_D) and anything that leads to the content (PacketHash or ContentHash). Each row assumes that party's **full state** is exposed, keys included.

| Party (fully exposed) | Holds | Cannot determine | Formal basis |
| --- | --- | --- | --- |
| Registry observer | ContentHash, verdict, any optional fields, F and I identities, coarse timestamp | Device; manufacturer | Property B |
| Addressed hop (A, D, G) | Device IP; timing; opaque payload | Device credential; content | Informal (structural) |
| Random hop (B, E, H) | Previous hop's address; destination | Device IP; credential; content | Informal (structural) |
| C | Token (opaque), key\_ref (manufacturer), PacketHash, BK, EncPH, verdict, σ\_V, tx\_id | cred\_D; ContentHash | Property D |
| V | cred\_D, tx\_nonce, claim, verdict, EncPH (opaque), tx\_id, C's network address | PacketHash; ContentHash | Property E, within one verdict class (see below) |
| G\_k | PacketHash, verdict, EncPH, BK, σ\_V, σ\_C, C's network address | cred\_D; ContentHash; which validator signed | Property J |
| Board reader | PacketHash, verdict, σ\_C, σ\_Gk | Device; manufacturer; ContentHash | Access is restricted to registry nodes by policy, not formally verified |
| F or I | ContentHash, n, PH', verdict, any optional fields, E's (or H's) address, board postings | Credential; manufacturer | Property F |
| Global passive observer | Sizes and timing only | Everything readable | Properties A–F, J (content); empirical timing evaluation separately |

### Two-party combinations that correlate (outside the t = 1 claim)

Only two pairs combine cred\_D with content:

- **V + C** — linked through tx\_id or EncPH.
- **V + any one G\_k** — linked through EncPH, which V receives from C and signs, and which G\_k also holds next to PacketHash in the clear.

**Pairs that do not correlate:** V + F or I (no shared value without BK); C + F or I, and G\_k + F or I (a shared PacketHash, but no device identity on either side).

**The verdict is a public attribute of the content.** It partitions the record population: an observer or a compromised V that sees a verdict few records share has fewer candidates. Every unedited hardware capture carries the same verdict, and decoys follow the real mix of verdicts. Property E holds within one verdict class. The symbolic model does not measure how much a rare verdict narrows the candidates.

**Network identity (device IP)** is not device identity under the target predicate, but it is a privacy concern. Only the first hops (A, D, G) see it, and they see no content.

## Registry record

A finalized record is **173 bytes** for a capture with no optional fields. Each optional field, the metadata hash and the parent ContentHash (edits only), adds 32 bytes: 205 bytes with either, 237 bytes with both.

| Field | Size | Notes |
| --- | --- | --- |
| ContentHash | 32 B | SHA-256 of the candidate image |
| verdict | 1 B | V's verdict: a modified bit and a four-class deviation bucket, zero for an unedited capture. Takes the byte the modification level held before |
| σ\_F | 64 B | Ed25519, F-id\_sk |
| σ\_I | 64 B | Ed25519, I-id\_sk |
| Server indices (F, I) | 2 × 2 B | Index into the registered server list, so the registry knows which keys to check at finalization |
| Timestamp | 8 B | Posting time, coarsened |
| h(metadata) (optional) | 32 B | Enables selective disclosure without putting values on-chain |
| Parent ContentHash (optional, edits only) | 32 B | Lets holders of both images check the relationship directly |

The record contains no device identifier, no manufacturer identifier, and no C or gatekeeper identity. It holds no signature from V, C or a gatekeeper: σ\_V never leaves C and the gatekeepers, and σ\_C and σ\_Gk stay on the boards. The verdict is covered only by σ\_F and σ\_I, as every other field is. It **does** name F and I. That is safe only because F and I are chosen independently of the device, the manufacturer and the jurisdiction.

**Sibling records:** one candidate image per transaction means a capture producing several candidate images (raw, ISP-processed, an adjustment) runs each through its own separate transaction, so their records may finalize close together. A registry observer could then link them to each other, though not to a device.

## Software-validator flow (summary)

An edited image uses the same 19 legs as a capture. The roles change: the editing application is the "device", and the software developer's server is V.

**Flow:**

1. The application opens a file that verifies against the registry.
2. It tracks every tool used and its intensity until save.
3. At save, it takes patches of the original, replays the recorded tools at the recorded intensities on those patches, and compares the result against the same patches of the saved image.
4. Mismatch produces a deviation score.
5. The application submits a new transaction for the saved image. The token carries the deviation score as its claim. The developer's server, acting as V, judges the claim and returns the verdict.

**Requirements this flow places on an implementation:**

- **The parent-record reference travels only in the content channel**, never the credential channel. Otherwise V (the developer) would hold the user's license credential next to a parent ContentHash, which is a single-party correlation.
- **Patch locations are chosen unpredictably, after edits are final.** Predictable patches would let edits outside them go undetected.
- **Software credentials are not hardware-rooted.** The hardware-extraction-resistance argument that holds for a capture device's credential does not apply here; this is a weaker guarantee for edited records than for captures.
- **The bucket boundaries are a deployment parameter.** The editing application and its developer set where one deviation class ends and the next begins. The protocol carries the resulting bucket and does not interpret it.
- **Threshold judgment is a one-party-managed tool, by necessity, not by oversight.** The developer's validator both runs the judgment software and enforces the threshold, with no independent check on that software's honesty. Co-developing judgment software with every participating developer is not tractable at scale; the accepted mitigation is that the devkit's rules are published and auditable, not that a second party checks each judgment. This is a distinct weakness from the hardware-rooting gap above, not the same one restated.
